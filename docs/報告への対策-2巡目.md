# 実機の報告（2巡目）に、何を原因と見て、どう直したか

1枚ずつの確認で挙がった **失敗2件・検証不能2件・機能不備3件・保留7件** に対する記録。

**「直した」と書いてあるものは、直しを外すと検査が落ちることまで確かめてある。**
落ちない検査は、何も守っていない。

## 失敗と報告されたもの

### 1. 全てのカードで《継召》が使えてしまう

> 全てのカードで継承ができるようになっている。正しくは、継承を持っているカードのみ継承を使える

**そのとおりだった。`継召判定` がカード側のキーワードを一度も見ていなかった。**

`継召判定` が見ていたのは次の2つだけ。

- 食べる側（トラッシュのカード）が EXシンボルを持つか
- 軽減シンボルの残り枠が足りているか

**発揮する側が《継召》を持っているか**は、どこにも書かれていなかった。
そのため「軽減シンボルさえあれば、どのカードでもトラッシュのEXシンボルを食べられる」
状態になっていた。

ルールブックの言う「共通効果」は *ルールブックに書かれている効果* という意味であって、
*全カードが持っている* という意味ではない。ここを取り違えていた。

**直し** … `継召判定.発揮できるか` を足し、《継召》を持たないカードは残り枠を 0 にした。
`除外できる最大枚数` も `除外は有効か` も残り枠から出しているので、
1か所で全部が閉まる。

**確かめ方** … 5つのデッキで自動対戦し、「トラッシュにEXシンボルがある場面」で
手札の全カードについて軽減できるかを数えた。

| | 直す前 | 直した後 |
|---|---|---|
| グン＝ガタ（《継召》なし）が軽減できた回数 | 20〜33回 | **0回** |
| ブレイククロー・フレイムハリケーン・紫21・飛傑レウファルス | 各1〜9回 | **0回** |
| 飛剛アクライ・飛赫レンシス・セルタリウス・オフェリングドロー（《継召》持ち） | 軽減できる | **軽減できる** |

条件が揃った場面が9〜33回あることを先に確かめてある。
0回のまま「食い違いなし」と出すと、何も確かめずに通ってしまう。

### 2. フレイムハリケーンの《ソウルマジック》が発動しない

**原因は3つ重なっていた。どれか1つでも残っていれば撃てない。**

**(a) 手札を押すことすらできなかった。**
画面が手札を押せるかどうかを `支払可能 || 場のコアも使えば支払えるか` で決めていた。
《ソウルマジック》はコストを丸ごと飛ばしてソウルコア1個で済ませる撃ち方なので、
コスト6ぶんのコアが無ければ**押せる条件をどれも満たさない**。
支払い画面まで辿り着けず、《ソウルマジック》の選択肢を見ることができなかった。

**(b) ソウルコアがリザーブに無いと使えないことになっていた。**
APIは `リザーブ保持者.ソウルコアあるか()` しか見ていなかった。
ソウルコアはスピリットの上に乗っていることが多く、しかも割り込みの窓のあいだは
コアを動かせない（メインステップ限定）。「場にソウルコアがあるのに撃てない」が起きる。

**(c) 画面が空の支払い指定を送り、APIがそれを「指定あり」と読んでいた。**

```js
// 画面が送っていたもの
支払い = { コスト: [], 継召除外: [], ソウルマジック: true }
```

```ts
// APIの読み方
const 指定 = 支払い?.コスト ? 組み立てる(支払い.コスト) : リザーブのソウルコア1個;
```

`[]` は真なので「指定あり」と読まれ、支払い元が **0件** になる。
《ソウルマジック》は支払い元の1つ目からソウルコアを出すので、0件なら必ず失敗する。

**直し**

- 画面：`ソウルマジックで使えるか` が立っていれば押せるようにした
- API：ソウルコアの居場所を「リザーブ＋自分の場のカードの上」に広げた
- API：`支払い元の指定あり()` を足し、中身が1件も無い一覧は「指定なし」と読む
- 画面：空の一覧はそもそも送らない
- 画面：《ソウルマジック》のときも支払い元を隠さず、どのソウルコアで払うかを選べるようにした

**確かめ方** … 820×1180 で起動直後から利用者が押せるものだけを辿った（種11）。

| | 結果 |
|---|---|
| 割り込みの窓を見た回数 | 10 |
| 窓のあいだに支払い画面を開けた回数 | 9 |
| 《ソウルマジック》で実際に撃てた回数 | **5** |
| 撃った結果 | 手札が1枚減り、相手の場が2→1に減り、ソウルコアがトラッシュへ移った |

## 検証不能と報告されたもの

### 3. ソウルコアを能動的にトラッシュに置けない（キュペルLv1/Lv2・飛赫レンシスLv2）

**支払い方を人が決める入口が、画面のどこにも無かった。**

`支払いを尋ねるべきか` は `window.設定.毎回支払いを選ぶ` を見ていたが、
**その `設定` を作っている場所がどこにも無い**（＝いつも自動）。
実装済みに見えて誰も呼んでいない、という形がまた出た。

そのためリザーブだけで払えるカードは黙って通常コアから払われ、
ソウルコアを狙ってトラッシュへ送ることができなかった。

**直し** … ターン表示の横に「支払い：自動 ／ 自分で選ぶ」の切り替えを置いた。
押すたびに切り替わり、次に開いたときも残る（localStorage）。

**確かめ方** … 「自分で選ぶ」にして自動対戦したところ、
リザーブのソウルコアを支払いに指定できる場面が7回あり、
試合の終わりにはトラッシュに **ソウルコアが置かれていた**。
種3・7・77でも同じ（毎回 `トラッシュのコア.ソウルコア: true`）。

これでキュペルLv1/Lv2・飛赫レンシスLv2を試す前提が整った。

### 4. フレイムハリケーンの［フラッシュ］の記載と、通常のフラッシュの記載が重なる

**そのとおりで、パネルが物理的に重なっていた。**

popover はどれも `position: fixed; left: 50%; top: 50%` で画面のまん中に置かれ、
z-index も全部 40。2枚出れば当然ぴったり重なる。

実際に測ると、割り込みの窓（420×133）が支払い画面（460×239）の中に
**すっぽり収まっていた**（重なりの面積 55,860px²）。文字がそのまま重なるので読めない。

前回、起動効果パネルと割り込みパネルの重なりを直したが、
**その2枚だけを直して、他の7枚を放っておいた**のが誤りだった。

**直し** … パネルを2種類に分けた。

| 種類 | 中身 | 決まり |
|---|---|---|
| 盤面のパネル | 割り込み・ブロック・効果の対象選択・起動効果 | 状態から出る |
| 人のパネル | 支払い・コア移動・トラッシュ・カードの説明 | 人が押して開く。**同時に1枚だけ** |

人のパネルが開いているあいだは盤面のパネルを引っ込め、閉じたら戻す。

**確かめ方** … 起動直後から辿り、全手番でパネルの枚数を数えた。
支払い画面を16回開き、うち9回は割り込みの窓が開いている最中。
**2枚以上出た場面は0回。**「やめる」で戻ると割り込みの窓が戻ることも毎回確かめた。

## 機能不備と報告されたもの

### 5. 別々のスピリットの上のソウルコアと通常コアを入れ替えられない

`コア管理.ソウルコアと通常コアを交換` は**前からあった**。呼び出し箇所はテストだけ。
またしても「実装済みに見えて誰も呼んでいない」だった。

そのため「ソウルコアを外す」→「通常コアを乗せる」の2手に分けるしかなく、
**途中でLv1のコストを割ったスピリットが消滅**してしまう。
コア1個のスピリット同士では事実上できなかった。

**直し** … `試合.ソウルコアと通常コアを入れ替える` → `/api/action/swap-core` →
コア移動パネルの「別のカードの通常コアと入れ替える」「リザーブの通常コアと入れ替える」。
2つの移動をまとめてから ルール処理 を呼ぶので、途中の一瞬で消滅しない。

**確かめ方** … 画面で、コア1個ずつの2体で入れ替えた。

```
前： グン＝ガタ(コア1・ソウル)   グン＝ガタ(コア1・通常)
後： グン＝ガタ(コア1・通常)     グン＝ガタ(コア1・ソウル)
```

**どちらも場に残っている。** 2手に分けていたころは、ここで片方が消滅していた。

### 6. 別領域のカードを表示するとき、画像の比率がおかしい

効果の対象を選ぶボタンは横長（458×74）で、そこにカード絵を**全面に敷いていた**。
`cover` なので縦横の比そのものは保たれるが、縦長のカード絵から横長の帯だけを
抜き出すことになり、何のカードか分からず比率もおかしく見えていた。

**直し** … デッキ構築の一覧と同じく、カードの形のまま縮めて先頭に置く。

**確かめ方** … 画面で測った。

| | 幅 | 高さ | 縦横比 |
|---|---|---|---|
| 直した後の絵柄 | 40px | 56px | **1.40** |
| 実物のカード（63mm×88mm） | ― | ― | 1.397 |

文字は絵の右に並び、絵の上に重なっていない。

### 7. ソウルコアを狙って払えない

→ 3番と同じ直し（「支払い：自分で選ぶ」）。

**場のスピリットの上に乗っているソウルコア**を指定して払うこともできる。

## ついでに見つかった、報告に無い不具合

### 8. ロワミークのデッキを選んでもグン＝ガタの試合が始まっていた

`/api/game/start` がデッキ名を**手書きの許可リスト**で照合し、
知らない名前は**黙って** `gungata` に差し替えていた。
そしてその許可リストから **`rowamique` が漏れていた**。

前回ロワミークのデッキを独立させたとき、デッキの型と作成関数は足したのに、

**直し** … デッキの名簿を1か所（`デッキタイプ一覧`）にまとめ、

それぞれで試合を始めて「グン＝ガタ以外のカードが1枚は出る」ことを見る検査を足した。
`rowamique` だけ差し替わるようにすると、この検査は落ちる（確認済み）。

**直し** … `メインで使えるか` を状態に足し、画面はそれを見て押せるかを決める。

## 追記：《ソウルマジック》がやはり撃てなかった

> フレイムハリケーンのソウルマジックが発動できません。フレイムハリケーン自体は発動できます

**支払い画面までは開くが、「これで出す」が押せない場面があった。**

原因は、《ソウルマジック》にチェックを入れたとき、
**リザーブにソウルコアがあるときだけ自動で選んでいた**こと。
スピリットの上に乗っているときは何も選ばれず、`コストに使うコア（0/1）` のまま
決定が押せない。しかもリザーブの行は、ボタンが1つも無い空の行として出るので、
何を押せばよいのかも分からなかった。

**ソウルコアは1人に1個しかない。** 「どのソウルコアで払うか」を選ばせても
選択肢は常に1つで、選ばせること自体に意味がなかった。

**直し** … チェックを入れたら、どこにあっても自動で選ぶ。
支払い元の一覧には、ソウルコアを持っている場所だけを出す。
見出しに「グン＝ガタ のソウルコア1個だけで使えます」と出どころを書く。

**確かめ方** … 820×1180 で、設定は既定（支払い：自動）のまま起動直後から辿った（種11）。

| | 直す前 | 直した後 |
|---|---|---|
| 窓のあいだに嵐を押せた | 6回 | 6回 |
| 《ソウルマジック》の欄が出た | 6回 | 6回 |
| **撃てた** | 5回 | **6回** |
| **撃てず**（決定が押せない） | **1回** | **0回** |

落ちていた1回は、ソウルコアがグン＝ガタの上にあった場面だった。

### あわせて：出せない札に理由を出す

残る「押せない」場面（ソウルコアがトラッシュにある等）は規則どおりだが、
**画面には何の説明も出ていなかった**。押しても無反応なので、
不具合なのか規則なのかを利用者が見分けられない。

出せない札も押せるようにして、理由を一言返す。

```
フレイムハリケーン：《ソウルマジック》に使うソウルコアが、
リザーブにも場のカードの上にもありません
フレイムハリケーン：《ソウルマジック》には自分の場に赤のシンボルが要ります
フレイムハリケーン は［フラッシュ］専用です。アタックやブロックの割り込みのときに使えます
```

理由はサーバーが返す（`出せない理由`）。画面が推測すると、実際の判定とずれる。

### どちらで払うかは選べる（既定は「実際に払えるほう」）

《ソウルマジック》と、ふつうにコストを払う出し方は、支払い画面のチェックで行き来できる。

ただし最初は必ず「ふつうに払う」側で開いていたため、
**コアが足りない場面でも `コストに使うコア（0/5）` のまま決定が灰色**になり、
チェックボックスに気づかないと手が止まった。撃てるほうを既定にする。

820×1180 で、同じ場面の両方を実際に押して確かめた（種11）。

| 場面 | ふつうに払えるか | 開いた直後の既定 | 切り替え |
|---|---|---|---|
| 手4・手18 | 払えない | **《ソウルマジック》**（決定できる） | 外せば通常側へ |
| 手23・手24 | リザーブで払える | **通常** | 入れれば《ソウルマジック》へ |
| 手30・手31 | 場のコアで払える | **通常** | 同上 |

## 追記：公開が「success」のまま止まっていた

PR #14 をマージしたあと、サイトが古い版のままだった。

```
8/6 12:49  push で公開が起動 → 組み立ては成功 → Pagesへの配置が10分で失敗
           ↓ しかし deployment の記録（1c90860）は残る
8/8 01:19  手で起こす → 「公開済み＝1c90860、変わっていない」 → 丸ごとスキップ
           ↓ 実行結果は success。サイトは 95f75b2 のまま
```

判定が `deployments` を1件見るだけで、**その公開が成功したかを見ていなかった**。
deployment の記録は配置が始まった時点で作られるので、失敗しても記録だけ残る。
一度失敗すると以後ずっと「変わっていない」と判断され、
**サイトは古いまま・実行結果は毎回 success** という、いちばん気づけない形で止まる。

**直し** … 新しい順に何件か辿り、状態が `success` のものだけを「公開済み」と数える。

**「実行結果が success」と「サイトが新しくなった」は別物。**
最後は必ず `版.json` の `印` を見ること。
