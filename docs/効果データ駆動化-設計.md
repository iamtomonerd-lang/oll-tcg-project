# 効果のデータ駆動化 — 設計方針

## 背景：なぜ設計を変えるのか

### 実測した現状コスト

ロワミーク（26RSD01-003）1枚を動かすために書いたコード：

| 内訳 | 行数 |
|---|---|
| ロワミーク専用（カード定義＋テスト＋専用条件クラス） | 167 |
| 効果基盤（対象選択・破壊・BP制限・フィールド検索＋テスト） | 447 |
| **合計** | **614** |

### 再利用率の実態

| 層 | 行数 | 割合 |
|---|---|---|
| 汎用層（`src/データ` + `src/効果処理`） | 928 | 14% |
| バトスピ専用層（`src/ゲーム例`） | 5,827 | 86% |

2つ目のTCGを実装するとき、86%を書き直すことになる。

### 破綻の見積もり

現行方式は **カード1枚 = クラス数個**。カードがN枚ならクラスがO(N)個増える。

- バトスピの主要カードを500枚に絞っても、1枚250行として12万行
- 1枚1時間でも3ヶ月フルタイム。対話ベースの実装ではその数倍
- さらに複数TCG展開でこれが繰り返される

**結論：現行方式ではスケールしない。**

### 隠れた地雷：対象選択の非同期性

対象選択はプレイヤー入力待ち＝非同期。現在はサーバーに `保留中の効果` を手で追加して対処しているが、
これをカードの種類ごとに書くと必ず破綻する。中断・再開は1箇所で解決すべき。

---

## 解決方針：カードを「データ」にして、エンジンが解釈する

実在のTCGシミュレータが全部たどり着いた形（遊戯王のYGOProはLua、MTGのForgeはカードスクリプトDSL）。

### 核心的な洞察

カードテキストは自然言語に見えて、**実際は有限の語彙の組み合わせ**。
約120個のプリミティブでバトスピのカードの9割がカバーできる。残り1割は個別スクリプト（逃げ道）。

### ビフォー／アフター

**現行（614行）**：カード定義 + 専用条件クラス + 対象選択クラス + 実行効果クラス + 各テスト

**データ駆動（15行）**：

```typescript
効果: [{
  Lv: [1, 2],
  トリガー: '召喚時',
  条件: { 存在: { 場: '自分', 状態: '疲労', 属性: '赤', 種別: 'スピリット' } },
  処理: [
    { 選択: { 場: '相手', 種別: 'スピリット', BP以下: 3000, 数: 1 } },
    { 破壊: '選択済み' },
  ],
}]
```

テストは不要（プリミティブ側で1回テスト済みのため）。

## 重要な発見：語彙はすでに実装済み

既存コードを調査した結果、**プリミティブに必要な操作はほぼ全て管理クラスとして存在している**。

- 管理クラス：42個（3,203行）
- 判定クラス：41個（1,494行）

インタプリタは、これらへの**薄いディスパッチ層**として実装できる。ゼロから作る必要はない。

### 行動プリミティブ（`管理/` から実測）

| プリミティブ | 実装元 |
|---|---|
| 破壊する / トラッシュへ置く | 破壊管理 |
| BPを設定 / 効果によるBPを変更 | BP管理 |
| 通常コアを移動 / ソウルコアを移動 / 全コアを移動 / ボイドからコアを置く | コア管理 |
| 回復する / 疲労する / 重疲労する | カードの表示形式管理 |
| シャッフルする / ドローする / 手札をデッキに戻す | デッキ管理 |
| 破棄する | 破棄管理 |
| Lvを上げる / Lvを下げる | Lv管理 |
| 配置する | 配置管理 |
| 待機状態にする | 待機状態管理 |

**約18個が実装済み。**

### フィルタ属性（`カードの情報/` + `判定/` から実測）

**静的属性**：Lv / カードナンバー / カード名 / カード種別 / コスト / シンボル /
ブロックアイコン / レアリティ / 作品アイコン / 属性 / 系統 / 軽減シンボル

**動的状態**：表示形式（回復・疲労・重疲労）/ BP / 現在Lv / コア数 / ソウルコア有無 / 待機状態

**比較演算**：以上 / 以下（`数値しきい値判定`）

**約17属性が参照可能。**

## 複数TCGで共有できるもの

「条件クラス」「効果クラス」は共有できない（ゲームごとに違う）。
共有できるのは **文法とインタプリタの骨格**：

1. トリガー → 条件 → 対象選択 → 処理 のパイプライン
2. 対象選択の解決機構（フィルタ合成・個数制約・**入力待ちの中断と再開**）
3. 効果の解決順序（スタック／チェーン）
4. カードデータのローダとバリデータ

推定1,500〜2,000行で**全TCG共通**。
各TCGは**語彙表（プリミティブの実装）だけ**を提供する（各300〜800行）。

2つ目のTCGは語彙を書くだけで済む。

## 既存資産の扱い

| 資産 | 扱い |
|---|---|
| 管理クラス群（BP管理・コア管理・ゾーン管理・Lv管理…） | **そのまま使う**。プリミティブがこれらを呼ぶ |
| 判定クラス群 | **そのまま使う**。フィルタがこれらを呼ぶ |
| 既存の効果クラス（破壊効果・BP上昇効果・ドロー効果） | **プリミティブの実装に転用** |
| ロワミークの実装 | **仕様の実例**としてプリミティブ設計の入力に |
| 「カードごとにクラスを作る」書き方 | **これだけ捨てる** |

## 次のステップ

### 1. カードテキストの語彙調査（← 現在ここ）

実物のバトスピカードのテキストを30〜50枚分集め、
**実際に必要なプリミティブが何個か**を実データで確定させる。

推測で設計すると必ず外すため、実物のテキストから逆算する。

### 2. プリミティブ仕様の確定

語彙調査の結果から、トリガー／条件／対象／処理の各カテゴリの語彙表を確定。

### 3. インタプリタ実装

既存の管理・判定クラスへのディスパッチ層として実装。
中断・再開の機構を1箇所に集約。

### 4. 既存4枚の移行

グンガタ／ゲン＝ボー／ムーシャッコ／ロワミークをデータ形式に書き換え、
同じ挙動になることを確認（リグレッションテスト）。
